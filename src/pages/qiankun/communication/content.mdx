## 一、引言

在微前端架构中，主应用和子应用运行在同一页面的不同生命周期中。它们共享同一个浏览器标签页，却拥有各自独立的 JavaScript 执行上下文和 DOM 区域。

这时候就会出现一个核心问题：

- **主应用的登录状态如何同步到子应用？**
- **子应用 A 修改了数据，子应用 B 怎么知道？**
- **主题色切换是否所有子应用都跟随？**

这些问题靠 iframe 的 `postMessage` 可以解决，但不够直观。qiankun 提供了两种内置的通信机制：**Props 通信**和**全局状态（GlobalState）**。

### 典型场景

- 主应用登录 → 所有子应用获取 token
- 主应用切换主题 → 所有子应用同步切换
- 子应用 A 修改了某些全局数据 → 子应用 B 需要感知

## 五、原理解析

### 5.1 发布订阅模式

`initGlobalState` 的核心机制是**发布-订阅模式**。qiankun 内部维护一个全局状态仓库和一个订阅者列表。

**核心流程：**

- `initGlobalState(state)`：创建一个全局状态仓库，内部维护一个 `state` 对象和一个 `observers`（Map）。
- `setGlobalState(newState)`：合并新状态到旧状态，遍历所有 observers 执行回调。
- `onGlobalStateChange(callback)`：将 callback 注册到 observers 中。
- `offGlobalStateChange()`：从 observers 中移除所有回调。

### 5.2 如何注入到子应用 props 中

qiankun 在加载子应用时，会将 `onGlobalStateChange` 和 `setGlobalState` 自动注入到子应用的 props 中。

也就是说，子应用收到的 props 中不仅包含 `registerMicroApps` 时传入的 props，还包含全局状态的接口。这就是为什么子应用在 mount 时可以直接 `props.onGlobalStateChange(...)`。

### 5.3 沙箱隔离对通信的影响

qiankun 的 JS 沙箱（`proxySandbox`）拦截了子应用的 window 操作。子应用内部的 `window.xxx = yyy` 不会暴露到主应用 window。

正因为沙箱隔离，子应用无法直接访问主应用的全局变量——所以才需要 `initGlobalState` 这种显式的通信机制。因此，`initGlobalState` 是**唯一受官方推荐**的跨应用通信方式（除了 props）。

### 5.4 fireImmediately 参数

- `fireImmediately = true`：注册后立即以当前 state 调用一次 callback。
- `fireImmediately = false` 或不传：只在 state 变化时才调用 callback。

在子应用初始化时，需要使用 `true` 来获取当前状态。

### 5.5 offGlobalStateChange 与内存泄漏

`offGlobalStateChange` 会清除该子应用的所有订阅者。但 `onGlobalStateChange` 返回的 `unsubscribe` 函数可以更精细地取消单个订阅。

**建议：** 在子应用 `unmount` 生命周期中取消订阅，防止内存泄漏。qiankun 在子应用 unmount 时会自动调用 `offGlobalStateChange`，但如果是通过 `loadMicroApp` 手动管理的子应用，需要自己调用 `unsubscribe`。
