## 一、为什么前端需要 Webpack？

<Typography.Paragraph>
  在 Webpack 出现之前，前端项目面临以下痛点：
</Typography.Paragraph>

<Card style={{ marginBottom: 24 }}>
  <Typography.Paragraph>
    - **模块化缺失：** 没有原生的模块系统（ES Modules 标准虽已提出，但浏览器支持慢），全局变量污染严重
  </Typography.Paragraph>
  <Typography.Paragraph>
    - **资源管理混乱：** CSS、图片、字体等非 JS 资源缺乏统一的管理和加载方式
  </Typography.Paragraph>
  <Typography.Paragraph>
    - **依赖管理困难：** 没有成熟的包管理工具配合，第三方库的管理和版本控制困难
  </Typography.Paragraph>
  <Typography.Paragraph>
    - **性能优化缺失：** 代码压缩、Tree Shaking、代码分割等现代优化手段完全空白
  </Typography.Paragraph>
  <Typography.Paragraph>
    - **开发体验差：** 缺少热更新、Source Map、开发服务器等提升效率的工具
  </Typography.Paragraph>
</Card>

`Webpack` 通过将一切视为**模块**（从 JS 到 CSS、图片、字体），并提供一个高度可扩展的**插件系统**，彻底解决了上述问题。它不仅是打包工具，更是**前端工程化的基石**。

      children: (
        <Typography.Paragraph>
          <strong>Loader</strong> 是<strong>文件转换器</strong>，运行在模块解析阶段，将不同类型的文件转换为 Webpack 可处理的模块（如 JS）。每个 Loader 是纯函数，职责单一。<br />
          <strong>Plugin</strong> 是<strong>功能扩展器</strong>，通过 Tapable 钩子介入构建的全生命周期，可以做任何 Loader 做不到的事情（如资源优化、环境变量注入、Bundle 分析）。
        </Typography.Paragraph>
      ),
    },
    {
      key: '3',

      children: (
        <Typography.Paragraph>

          输出质量方向：`Tree Shaking`、`Code Splitting`（`SplitChunksPlugin`）、`Scope Hoisting`、压缩（`TerserWebpackPlugin` / `CSSMinimizerWebpackPlugin`）、`Gzip` / `Brotli` 预压缩。
        </Typography.Paragraph>
      ),
