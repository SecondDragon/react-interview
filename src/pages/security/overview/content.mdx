## 七、常见面试问题方向

<Collapse
  style={{ marginBottom: 24 }}
  items={[
    {
      key: '1',
      label: 'XSS 和 CSRF 的区别是什么？（高频）',
      children: (
        <Typography.Paragraph>
          <strong>攻击目标不同：</strong>XSS 的目标是<strong>受害者浏览器</strong>——注入脚本执行任意代码；CSRF 的目标是<strong>Web 应用服务器</strong>——伪造用户请求。<br />
          <strong>利用机制不同：</strong>XSS 利用的是<strong>站点对用户输入的信任</strong>（未过滤直接输出）；CSRF 利用的是<strong>站点对浏览器的信任</strong>（浏览器自动携带 Cookie）。<br />
          <strong>攻击结果不同：</strong>XSS 可以做到 CSRF 做不到的事（如读取页面 DOM、键盘记录、修改页面内容）；CSRF 只能发送请求，无法读取响应（受同源策略限制）。<br />
          <strong>防御手段对比：</strong>CSRF Token 能防 CSRF 但不能防 XSS（XSS 可以读取 Token）；HttpOnly Cookie 能防 XSS 窃取 Session 但不能防 CSRF（浏览器仍携带 Cookie 发请求）。
        </Typography.Paragraph>
      ),
    },
    {
      key: '2',
      label: 'CSP 中 nonce 和 hash 的区别？什么场景用哪个？',
      children: (
        <Typography.Paragraph>
          <strong>nonce（Number Used Once）：</strong>服务端每次响应时生成一个随机数，嵌入到 CSP 头和 script 标签的 nonce 属性中。攻击者无法预测 nonce 值，因此注入的 script 标签不会被浏览器执行。<strong>适用于动态生成的内联脚本</strong>（如服务端渲染时的初始化脚本）。<br />
          <strong>hash：</strong>对内联脚本的内容计算 SHA-256/SHA-384/SHA-512 哈希，放入 CSP 头的 script-src 中。浏览器执行前会重新计算哈希并比对。<strong>适用于静态内联脚本</strong>（内容不变，如 webpack 的 inline chunk）。<br />
          <strong>重要限制：</strong>nonce 必须是密码学安全的随机数且不可预测。攻击者唯一能绕过 nonce 的方式是在已存在的 nonce 脚本标签中注入代码——DOM Clobbering 就是利用这一点的攻击。
        </Typography.Paragraph>
      ),
    },
    {
      key: '3',
      label: 'SameSite Cookie 的三个值分别是什么意思？',
      children: (
        <Typography.Paragraph>
          <strong>Strict（最严格）：</strong>完全禁止跨站请求携带 Cookie。用户从其他站点点击链接到目标站点时也不会携带，导致登录态丢失。适用于银行等对安全要求极高的场景。<br />
          <strong>Lax（Chrome 默认）：</strong>允许「顶级导航的 GET 请求」携带 Cookie——即用户点击链接、或通过 {'<a>'} 标签跳转。POST 请求、iframe、img 标签、fetch/XMLHttpRequest 等子资源请求不携带。是安全与体验的最佳平衡点。<br />
          <strong>None（最宽松）：</strong>所有跨站请求都携带 Cookie，但<strong>必须同时设置 Secure 属性</strong>（仅 HTTPS 传输），否则 Chrome 会拒绝。适用于需要跨站嵌入的资源（如第三方支付页面的 iframe）。
        </Typography.Paragraph>
      ),
    },
    {
      key: '4',
      label: 'localStorage 存 JWT Token 有什么安全问题？应该怎么存？',
      children: (
        <Typography.Paragraph>
          localStorage 存 Token 的核心问题：<strong>任何 JS 代码都能读取</strong>。一旦发生 XSS，Token 直接暴露。而 HttpOnly Cookie 虽然防 XSS 读取但不能防 CSRF。
          <br /><br />
          <strong>推荐方案（BFF 模式）：</strong><br />
          1. Access Token + Refresh Token 都存储在后端 Session 中。<br />

          2. Refresh Token 存 httpOnly Cookie，配合 CSRF Token + SameSite=Lax。<br />
          3. 定期轮换 Refresh Token（Refresh Token Rotation）。
