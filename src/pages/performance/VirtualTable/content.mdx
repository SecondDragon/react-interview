## 二、性能问题出现的底层原因

<Card style={{ marginBottom: 16 }}>
  <Typography.Title level={5}>1. DOM 节点过多导致布局风暴（Layout Thrashing）</Typography.Title>
  <Typography.Paragraph>
    当浏览器一次性创建 10000+ 个 <Typography.Text code>{'<tr>'}</Typography.Text> 节点时，需要为每个节点计算布局信息。每做一次样式变更或滚动，浏览器都会触发 reflow 重新计算所有节点位置。这个过程的计算量随节点数线性增长，导致主线程被长时间占用。
  </Typography.Paragraph>

  <Typography.Title level={5}>2. React Reconciliation 瓶颈</Typography.Title>
  <Typography.Paragraph>
    React 的 diff 算法虽然高效，但它的比较复杂度与虚拟 DOM 树大小成正比。当整个表格包含 10000+ 行时，即使只更新一个复选框状态，React 也需要遍历所有行来比较是否需要更新 DOM。这就是为什么勾选"全选"会卡顿——因为 React 正在对比 10000+ 个 <Typography.Text code>row</Typography.Text> 的 props。
  </Typography.Paragraph>

  <Typography.Title level={5}>3. 滚动事件高频触发导致重绘</Typography.Title>
  <Typography.Paragraph>
    滚动事件以每秒约 60 次的频率触发，每一次触发都可能触发浏览器的 repaint/reflow。如果每一帧都需要操作大量 DOM，帧绘制时间会超过 16.67ms（60fps 的预算），导致掉帧和视觉卡顿。
  </Typography.Paragraph>
</Card>

## 六、核心原理解释

<Card style={{ marginBottom: 16 }}>
  <Typography.Title level={5}>虚拟滚动的运行流程</Typography.Title>
  <Typography.Paragraph>
    当你滚动表格时，<Typography.Text code>useVirtualizer</Typography.Text> 内部经历以下五个步骤：
  </Typography.Paragraph>

  <Steps
    direction="vertical"
    current={-1}
    items={principleSteps}
  />

  <Divider />

  <Typography.Title level={5}>关键细节：为什么用 translateY 而不是 scrollTop</Typography.Title>
  <Typography.Paragraph>
    很多开发者会疑惑：为什么要把所有虚拟行放在一个 <Typography.Text code>position: relative</Typography.Text> 容器里，然后用 <Typography.Text code>translateY</Typography.Text> 定位？直接用 <Typography.Text code>scrollTop</Typography.Text> 控制行的位置不行吗？
  </Typography.Paragraph>
  <Typography.Paragraph>
    答案在于浏览器的渲染机制。当使用 <Typography.Text code>transform: translateY</Typography.Text> 时，浏览器会将该元素提升为**合成层（Compositing Layer）**，后续的位置变化只触发合成阶段的重新定位，而**不会触发 Layout（重排）和 Paint（重绘）**。这意味着每次滚动更新行位置时，性能开销极小。
  </Typography.Paragraph>
  <Typography.Paragraph>
    相反，如果通过修改 <Typography.Text code>marginTop</Typography.Text> 或 <Typography.Text code>top</Typography.Text> 来定位，每次变化都会触发重排，性能会差很多。
  </Typography.Paragraph>

  <Divider />

  <Typography.Title level={5}>Overscan 的权衡</Typography.Title>
  <Typography.Paragraph>
    <Typography.Text code>overscan</Typography.Text> 控制视口外额外渲染的行数。设置较大的值（如 300）可以防止快速滚动时出现白屏，但会多渲染一些 DOM。设置较小的值（如 5）可以减少冗余渲染，但快速滚动时可能出现短暂的白屏。
  </Typography.Paragraph>
  <Typography.Paragraph>
    在 <Typography.Text code>Live Demo</Typography.Text> 中我们设置 <Typography.Text code>overscan: 300</Typography.Text>，因为数据量较大且每行很轻量，保险起见多渲染一些更流畅。生产环境中可以根据滚动速度和行高复杂度灵活调整。
  </Typography.Paragraph>

  <Divider />

  <Typography.Title level={5}>TanStack Table 与 TanStack Virtual 的分工</Typography.Title>
  <Typography.Paragraph>
    两者的分工是整个架构的精髓：
  </Typography.Paragraph>
  <List
    dataSource={[
      {
        label: 'TanStack Table',
        desc: '负责"逻辑层"——数据模型、列定义、排序、过滤、勾选状态管理等。它不关心 DOM 如何渲染，只维护一个 JS 状态树。',
      },
      {
        label: 'TanStack Virtual',
        desc: '负责"展示层"——计算出当前视口应该显示哪些行。它不关心数据内容，只关心行索引和位置。',
      },
    ]}
    renderItem={(item) => (
      <List.Item>
        <Typography.Paragraph style={{ marginBottom: 0 }}>
          <Typography.Text strong>{item.label}</Typography.Text>
          <br />
          <Typography.Text type="secondary">{item.desc}</Typography.Text>
        </Typography.Paragraph>
      </List.Item>
    )}
  />
  <Typography.Paragraph style={{ marginTop: 16 }}>
    两者的结合点是一个简单的数组索引：<Typography.Text code>{'const row = rows[virtualRow.index]'}</Typography.Text>。TanStack Table 提供所有行的数据，TanStack Virtual 告诉 React "只看渲染这几行"，于是 React 只需要遍历几行而不是上万行。
  </Typography.Paragraph>
</Card>
