## 二、性能问题出现的底层原因

<Card style={{ marginBottom: 16 }}>
  <Typography.Title level={5}>1. React.lazy 的"懒"是真正的"不加载"</Typography.Title>
  <Typography.Paragraph>
    <Typography.Text code>React.lazy(() => import('./HeavyPage'))</Typography.Text> 中的 <Typography.Text code>import()</Typography.Text>
    函数是惰性求值的——它只在组件首次渲染时才会被调用。也就是说，只要用户不点击导航到该路由，
    对应的 JS chunk 就**永远不会被下载**。这是优点也是缺点：首屏干净了，但用户点击时的网络延迟无可避免。
  </Typography.Paragraph>

  <Typography.Title level={5}>2. JS 解析与执行的同步阻塞</Typography.Title>
  <Typography.Paragraph>
    浏览器下载完 JS chunk 后，还需要经过解析（Parse）、编译（Compile）、执行（Execute）三个阶段，
    这些都在主线程上同步进行。对于重型页面（ECharts、Monaco Editor 等），一个 chunk 可能达到几百 KB，
    解析执行耗时可能达到几百毫秒。这段时间内，用户界面完全被阻塞。
  </Typography.Paragraph>

  <Typography.Title level={5}>3. 网络延迟的不确定性</Typography.Title>
  <Typography.Paragraph>
    无论你使用 CDN 还是部署在同一机房，网络请求始终存在延迟。在高延迟网络（如移动端 4G）下，
    即使是几十 KB 的小 chunk，也可能耗费 500ms 以上。如果 chunk 体积较大（如 200KB+），
    在弱网环境下用户等待 3-5 秒是常有的事。
  </Typography.Paragraph>

  <Typography.Title level={5}>
    <Typography.Text code>requestIdleCallback</Typography.Text> 的工作原理
  </Typography.Title>

  <Typography.Paragraph>
    浏览器的主线程以每帧约 16.67ms（60fps）的节奏工作。在一帧中，浏览器需要完成：输入事件处理 → JS 执行 → Style 计算 → Layout → Paint → Composite。
    如果上述任务完成后还有剩余时间，<Typography.Text code>requestIdleCallback</Typography.Text> 的回调就会被执行。
  </Typography.Paragraph>

  <Typography.Paragraph>
    这一帧的剩余时间可以通过 <Typography.Text code>deadline.timeRemaining()</Typography.Text> 获取。
    同时，可以通过 <Typography.Text code>timeout</Typography.Text> 参数设置"防饿死"机制——如果在指定时间内一直没有空闲帧，浏览器也会强制执行回调。
  </Typography.Paragraph>

  <Divider />

  <Typography.Title level={5}>关键细节：为什么 import() 预取不如 <Typography.Text code>{'<link rel="prefetch">'}</Typography.Text> 轻量</Typography.Title>

  <Typography.Paragraph>
    Webpack 的 <Typography.Text code>{'/* webpackPrefetch: true */'}</Typography.Text> 生成的是 <Typography.Text code>{'<link rel="prefetch">'}</Typography.Text> 标签，
    浏览器只会<strong>下载</strong>资源到缓存，<strong>不会解析和执行</strong>。这非常轻量，几乎不消耗 CPU。
  </Typography.Paragraph>

  <Typography.Paragraph>
    而我们的 <Typography.Text code>IdlePrefetch</Typography.Text> 组件在 <Typography.Text code>requestIdleCallback</Typography.Text> 中执行的是 <Typography.Text code>import()</Typography.Text>，
    这会触发 JS 模块的完整加载流程：下载 → 解析 → 编译 → 执行。虽然模块的头文件很小（动态导入的 chunk 入口），
    但在主线程上仍然有解析开销。这是 Vite 生态下无法避免的——Vite 没有 <Typography.Text code>webpackPrefetch</Typography.Text> 等效的构建期解决方案。
  </Typography.Paragraph>

  <Typography.Paragraph>
    不过，这个解析开销相比用户点击时的同步等待要小得多——因为预取时主线程可能处于空闲状态，
    此时解析模块不会影响用户体验。这就是"用空闲 CPU 换未来体验"的核心思想。
  </Typography.Paragraph>
