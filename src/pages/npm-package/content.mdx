<Typography.Title level={2}>npm 包封装完全指南</Typography.Title>

当你写好了一个 React 组件，想把它的成果分享给其他团队或开源社区，你就需要把它封装成一个 npm 包。封装看似简单——跑个构建然后 npm publish 就行——但其中涉及字段配置、构建工具选型、格式转换、版本管理等诸多环节。本文从零开始，把"组件到 npm 包"的完整链路讲透。

## 一、概念与背景

### 1.1 什么是 npm 包

npm 包本质上是一个包含 `package.json` 的目录，经过 `npm publish` 上传到 npm registry，其他人可以通过 `npm install` 下载使用。

当你封装一个组件为 npm 包时，你需要考虑：

- **多方消费者**：使用者的项目可能是 CJS（require）、ESM（import）、TypeScript（需要类型声明）、或 CDN（UMD/IIFE）
- **构建与源码分离**：你写的是 `.tsx` / `.ts`，但使用者需要的是编译后的 `.js` + 类型声明 `.d.ts`
- **依赖关系**：React 这类运行时依赖不应被打包进去，而是作为对等依赖让宿主环境提供

### 1.2 为什么要封装为 npm 包

<Card style={{ marginBottom: 24 }}>

- **代码复用**：一次封装，多项目复用。修改源码后仅需发布新版本
- **版本管理**：通过 semver 语义化版本控制，使用者可锁定或灵活升级
- **关注点分离**：组件仓库独立维护，不耦合于业务项目
- **Tree Shaking**：通过 ESM 格式输出，打包工具可以摇掉未使用的代码
- **类型安全**：发布 `.d.ts` 后，使用者在 IDE 中获得完整类型提示

</Card>

**核心原则：**
- `src/` 是源码（开发者编写），`dist/` 是构建产物（使用者引用）
- `package.json` 是包的"身份证"，所有入口信息都在这里定义
- `npm publish` 默认会发布 `package.json` + `README.md` + `files` 白名单内的文件

### 2.2 package.json 核心字段详解

package.json 中有几个字段直接决定了"使用者怎么用你的包"，这是封装 npm 包最核心的知识点：

**重点理解 `exports` 字段的优先级机制：**

当使用者写 `import 'my-button'` 时，Node.js 或打包工具会按以下顺序查找入口：

1. 先看 `exports["."]` 是否有条件导出
2. 根据环境匹配条件：`import` → `require` → `types` → `default`
3. 如果无 `exports`，回退到 `module` 字段（仅打包工具支持）
4. 再回退到 `main` 字段

这就是为什么**推荐使用 `exports` 字段**——它提供了最精确的入口控制和环境隔离。

## 三、封装方案详解：三种构建工具对比

封装 npm 包的核心任务是：**把 TypeScript/TSX 源码编译成 JS，同时生成类型声明文件**。解决这个问题有三种主流工具，它们各有优缺点。

## 四、构建流程全景图

不论使用哪种工具，从源码到 npm registry 的完整链路都是一致的：

<MermaidViewer source={buildPipeline} />

三个工具的共同点：

- 都需要将 TypeScript 编译为 JavaScript
- 都需要生成类型声明文件（.d.ts）
- 都需要通过 npm publish 将产物上传到 registry

三者的核心差异在于 **"编译+打包"是否由同一个工具完成**：

- tsup：esbuild 一站式完成（编译 + bundle + 多格式 + dts）
- Rollup：Rollup + 多个插件组合完成
- tsc：仅完成编译，打包需额外工具

## 七、核心原理总结

### 7.1 构建工具的核心职责

不管使用什么工具，封装 npm 包时构建工具需要解决三个核心问题：

1. **格式转换**：TypeScript → JavaScript、TSX → JSX/JS
2. **模块整合**：多个源文件 → 单一输出文件（bundle），或按需输出多文件
3. **元信息生成**：类型声明 `.d.ts`、Source Map、压缩包

### 7.2 为什么需要双格式输出（ESM + CJS）

JavaScript 生态目前处于 ESM 和 CJS 并存的过渡期：

- **使用者的项目可能是 CJS**（Node.js 传统项目，通过 require 加载）
- **使用者的项目可能是 ESM**（现代项目，通过 import 加载，支持 tree-shaking）
- **使用者的构建工具不同**（Webpack 5 优先使用 module 字段，Rollup 优先使用 exports.import）

因此，"一个组件库发布时需要同时提供 `.js`（CJS）和 `.mjs`（ESM）两份构建产物"是当前的最佳实践。tsup 的 `--format esm,cjs` 就是干这件事的。

### 7.3 sideEffects 与 Tree Shaking 的关系

`sideEffects: false` 告诉打包工具："这个包的所有模块都没有副作用，可以安全地删除未使用的导出"。

**副作用**指模块在导入时就会执行的代码（不依赖任何导出），例如：

<CodeDiff
  oldValue="import './global.css'    // 即使不导出任何内容，也会执行 CSS 注入"
  newValue="import { Button } from 'my-button'  // 如果只用了 Button，Input 的代码会被 tree-shaking 掉"
  leftTitle="有副作用的导入"
  rightTitle="无副作用的导入"
  type="warning"
  hideDiffMarkers={true}
/>

如果你的包引入了全局 CSS 或有模块级副作用代码（如 `Object.defineProperty` 操作），需要正确标记 `sideEffects` 数组，而不是简单地写 `false`：

{`// 只有特定文件有副作用
"sideEffects": [
  "./dist/global.css",
  "./dist/polyfill.js"
]`}
</pre>

## 总结：一句话建议

| 场景 | 推荐方案 |
|---|---|
| 新项目、中小型组件库 | **tsup**（零配置、速度快、够用） |
| 大型组件库、需要 UMD 输出 | **Rollup**（tree-shaking 最强、插件生态丰富） |
| 纯类型库或学习用途 | **tsc**（最简单、无额外依赖） |
